## Lernziele

Nach dieser Übung kannst du

- den Unterschied zwischen asynchroner Replikation (Hyper-V-Replica) und echter Hochverfügbarkeit in einem Windows Server Failover Cluster erklären
- die Kernkomponenten eines Hyper-V-Failover-Clusters (Clusterknoten, Cluster-Netzwerke, Quorum und Zeugen/Witness, Cluster Shared Volumes / CSV) erläutern
- das Feature `Failover-Clustering` installieren, einen Cluster-Validierungstest (`Test-Cluster`) durchführen und die Ergebnisse auswerten

## Voraussetzungen

- Abschluss von Modul 8 (Modul 9 und 10 werden empfohlen, sind aber nicht zwingend)

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Failover-Cluster** | Gruppe von Servern (Knoten), die Rollen bei Ausfall übernehmen |
| **Knoten** | einzelner Server im Cluster |
| **CSV** | Cluster Shared Volume; gleichzeitiger Zugriff mehrerer Knoten, eingehängt unter `C:\ClusterStorage\` |
| **Quorum** | Mehrheitsentscheidung, die einen Split-Brain verhindert |
| **Witness** | zusätzliche Stimme (Disk, Dateifreigabe, Cloud) |
| **VHD-Set (`.vhds`)** | gemeinsam nutzbare virtuelle Festplatte für Gastcluster |
| **`Test-Cluster`** | Prüfung der Cluster-Voraussetzungen |

| Was | Rolle in Modul 11 |

## Aufgabe

### Aufgabe 1 – Installation des Features Failover-Clustering auf den verschachtelten Hosts (Einheit 11.1, Einheit 11.4)

Installieren Sie innerhalb der beiden Gast-VMs `VM-SRV01` und `VM-SRV02` das Windows-Feature `Failover-Clustering` inklusive der Verwaltungswerkzeuge per PowerShell:
`Install-WindowsFeature -Name Failover-Clustering -IncludeManagementTools`

### Aufgabe 2 – Konfiguration einer gemeinsamen VHDX-Set-Datei (`.vhds`) als simulierter Shared Storage (Einheit 11.2)

Erstellen Sie auf dem Basishost `HV-HOST01` eine gemeinsame virtuelle Festplatte im VHD-Set-Format (`New-VHD -Path C:\HyperV\VHDs\ClusterSharedDisk.vhds -SizeBytes 10GB -Dynamic`). Hängen Sie diese `.vhds`-Datei an die SCSI-Controller von **beiden** Gast-VMs (`VM-SRV01` und `VM-SRV02`) mit aktivierter Option für gemeinsame Datenträgernutzung (`Add-VMHardDiskDrive -ShareVirtualDisk`) an.

### Aufgabe 3 – Cluster-Validierung eines Einzelknotens (Einheit 11.3, Einheit 11.4)

Führen Sie auf `VM-SRV01` `Test-Cluster -Node VM-SRV01` aus und öffnen Sie den HTML-Bericht unter `C:\Windows\Cluster\Reports`. Erwartung: Im Workgroup-Labor mit nur einem Knoten enthält der Bericht Warnungen oder Fehler (z. B. nur ein Knoten, keine Domänenmitgliedschaft, kein bestätigter gemeinsamer Speicher). Ordnen Sie jede Meldung einer Anforderung aus 11.2 bis 11.4 zu und notieren Sie, welche Anforderung das Labor nicht erfüllt. Eine Clusterbildung (`New-Cluster`) ist nicht Ziel der Übung. Bricht `Test-Cluster` schon vor der Berichtserstellung mit einer Fehlermeldung ab, dokumentieren Sie die Meldung und ihre Ursache.

### Aufgabe 4 – Rückbau der Änderungen aus Modul 11 (Einheit 11.2)

Fahren Sie `VM-SRV01` und `VM-SRV02` herunter, trennen Sie `ClusterSharedDisk.vhds` von beiden VMs (`Remove-VMHardDiskDrive`) und löschen Sie die `.vhds`-Datei samt Begleitdateien im selben Ordner auf `HV-HOST01`. Starten Sie beide VMs und deinstallieren Sie darin das Feature (`Uninstall-WindowsFeature -Name Failover-Clustering -IncludeManagementTools -Restart`). Der übrige Rückbau der Nested-Umgebung erfolgt in Modul 12, Aufgabe 1.

## Hinweise

- `New-Cluster` ist nicht Ziel der Übung; es wird nur validiert.
- Ob `New-VHD` für `.vhds` den Schalter `-Dynamic` annimmt und ob das Anhängen am laufenden System funktioniert, ist **nicht bestätigt**; bei einer Fehlermeldung diese festhalten.
- Bricht `Test-Cluster` schon vor dem Bericht ab, dokumentiere die Meldung und ihre Ursache (Lehrplan).
- Der Rückbau (Aufgabe 4) ist Pflicht; der übrige Rückbau der Nested-Umgebung folgt in Modul 12.
- Einheit 11.1 (Hochverfügbarkeit) wird über die Kontrollfrage 3 erarbeitet.

## Kontrollfragen

1. Welches Problem löst ein *Cluster Shared Volume (CSV)* in einem Hyper-V-Cluster im Vergleich zu einer klassischen NTFS-formatierten LUN, auf die immer nur ein Server gleichzeitig zugreifen darf?
2. Was versteht man in einem Cluster unter einem *Split-Brain-Szenario*, und wie verhindert das Quorum (z. B. mithilfe eines File Share Witness oder Disk Witness) diesen Zustand?
3. Was geschieht mit einer hochverfügbaren virtuellen Maschine in einem Hyper-V-Failover-Cluster, wenn der physische Host, auf dem sie gerade läuft, durch einen plötzlichen Stromausfall hart ausfällt?
4. Warum sollte vor der produktiven Inbetriebnahme eines Hyper-V-Clusters immer der Cluster-Validierungsassistent (`Test-Cluster`) vollständig und ohne Fehler durchlaufen werden?

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Installation des Features Failover-Clustering auf den verschachtelten Hosts).** ```powershell
$cred = Get-Credential
foreach ($vm in 'VM-SRV01','VM-SRV02') {
  Invoke-Command -VMName $vm -Credential $cred -ScriptBlock { Install-WindowsFeature -Name Failover-Clustering -IncludeManagementTools }
}
```

Zielzustand: Feature in beiden VMs installiert (`Get-WindowsFeature Failover-Clustering` zeigt `Installed`); je nach Ergebnis ist ein Neustart nötig. Zu 11.1: Notiere den Unterschied: Live-Migration verschiebt geplant, der Cluster startet eine ausgefallene VM automatisch neu.

**Aufgabe 2 (Konfiguration einer gemeinsamen VHDX-Set-Datei (`.vhds`) als simulierter Shared Storage).** Auf `HV-HOST01`:

```powershell
New-VHD -Path C:\HyperV\VHDs\ClusterSharedDisk.vhds -SizeBytes 10GB -Dynamic
Add-VMHardDiskDrive -VMName VM-SRV01 -ControllerType SCSI -Path C:\HyperV\VHDs\ClusterSharedDisk.vhds -ShareVirtualDisk
Add-VMHardDiskDrive -VMName VM-SRV02 -ControllerType SCSI -Path C:\HyperV\VHDs\ClusterSharedDisk.vhds -ShareVirtualDisk
Get-VMHardDiskDrive -VMName VM-SRV01, VM-SRV02 | Select-Object VMName, Path
```

`-ShareVirtualDisk` ist laut Referenz ein Alias von `-SupportPersistentReservations`. Zielzustand: Die Set-Datei hängt an beiden VMs. Zu 11.2: Erkläre in zwei Sätzen, warum ein Cluster gemeinsamen Speicher braucht und wofür CSV dient.

**Aufgabe 3 (Cluster-Validierung eines Einzelknotens).** In `VM-SRV01`:

```powershell
Test-Cluster -Node VM-SRV01
Get-ChildItem C:\Windows\Cluster\Reports
```

Erwartete Befunde (geplant, nicht gemessen): Warnungen oder Fehler zu fehlender Domäne, nur einem Knoten, nicht bestätigtem gemeinsamen Speicher und fehlenden Netzwerkpfaden. Ordne jede Meldung einer Anforderung aus 11.2 bis 11.4 zu (Knoten, gemeinsamer Speicher/CSV, Quorum/Witness, Validierung). Lege dazu eine Tabelle *Meldung / Anforderung / Labor erfüllt?* an.

**Aufgabe 4 (Rückbau der Änderungen aus Modul 11).** ```powershell
Stop-VM -Name VM-SRV01, VM-SRV02
Get-VMHardDiskDrive -VMName VM-SRV01 | Where-Object Path -like '*ClusterSharedDisk*' | Remove-VMHardDiskDrive
Get-VMHardDiskDrive -VMName VM-SRV02 | Where-Object Path -like '*ClusterSharedDisk*' | Remove-VMHardDiskDrive
Get-ChildItem C:\HyperV\VHDs -Filter 'ClusterSharedDisk*'
# Dateien prüfen und löschen:
Remove-Item C:\HyperV\VHDs\ClusterSharedDisk* -Force
Start-VM -Name VM-SRV01, VM-SRV02
# danach in beiden VMs:
Uninstall-WindowsFeature -Name Failover-Clustering -IncludeManagementTools -Restart
```

Vor dem Löschen mit dem Filter `ClusterSharedDisk*` kontrollieren, dass nur die Set-Datei und ihre Begleitdateien betroffen sind. Zielzustand: keine Datei, kein Feature, keine Anbindung.

**Fragen.** (1) Bei einer klassischen LUN darf immer nur ein Server gleichzeitig zugreifen. Ein CSV erlaubt mehreren Knoten den gleichzeitigen Zugriff auf dieselbe Platte (eingehängt unter `C:\ClusterStorage\`), sodass VMs ohne Umkonfiguration zwischen Knoten wechseln können (Lehrplan 11.2; Einzelheiten nicht geprüft). (2) Split-Brain: Fällt die Verbindung zwischen Knotengruppen aus, könnten beide Gruppen glauben, aktiv zu sein, und dieselben VMs starten; das kann Daten zerstören. Das Quorum erlaubt nur der Gruppe mit der Mehrheit der Stimmen (Knoten plus Disk-, Dateifreigabe- oder Cloud-Witness) weiterzuarbeiten (Lehrplan 11.3). (3) Ist die VM hochverfügbar, erkennt der Cluster den Ausfall und startet sie automatisch auf einem anderen Knoten neu; der Neustart entspricht einem harten Absturz (Lehrplan 11.1). (4) `Test-Cluster` prüft Server, Netzwerk, Speicher und Software auf Clustertauglichkeit; Fehler vor der Inbetriebnahme verhindern spätere Ausfälle. Warnungen sind zu bewerten, nicht blind zu übergehen (Fachwissen).
